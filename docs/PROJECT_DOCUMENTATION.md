# FitFlow Project Documentation

This is the living technical and product record for FitFlow. Update this document in the same change whenever behavior, architecture, dependencies, data structures, testing practices, or design principles change.

## 1. Product Origin

FitFlow began from `Workout-App-PRD-and-Build-Plan.md`. The original goal was to remove the friction of manually setting exercise and rest timers while following a weekly workout schedule.

The core product principles are:

- A workout should begin in one or two taps.
- Timing and transitions should require as little manual input as possible.
- Rep-based exercises wait for user confirmation; timed exercises advance automatically.
- Timer accuracy must be based on timestamps, not accumulated interval ticks.
- Scheduled rest days must not break streaks.
- Audio cues must always have an equivalent visible state.
- The interface must remain readable and operable on a propped-up phone.
- Plans and player behavior must be data-driven rather than hard-coded.

## 2. Delivery History

### Initial MVP

The first implementation established:

- React, TypeScript, and Vite.
- A mobile-first Today, Plan, and Progress experience.
- A guided workout player with rep and timed exercises.
- Timestamp-based countdowns, pause/resume, partial completion, and session history.
- Web Audio cues and best-effort Screen Wake Lock.
- Local persistence through `localStorage`.
- An installable PWA generated by `vite-plugin-pwa`.
- A default upper-body and core workout.

### Workout skipping

The Today screen gained a confirmed “Skip today” flow. Skipped sessions are stored separately from completed and partial sessions and do not increment completion totals or streaks.

### Dynamic plan system

The hard-coded workout was replaced with a plan model supporting:

- Plan creation, editing, loading, and deletion.
- Required and optional workout days.
- Optional section names.
- Multiple exercises per section.
- Rep or timed exercise modes.
- Sets, rep labels, estimated work duration, rest duration, and coaching notes.
- Live calculated duration, set, and section totals.
- Plan-specific history and streaks.

### Intermediate upper-body plan

The supplied “Full Upper Body + Core Workout (Intermediate)” routine was encoded as the built-in plan. Monday and Wednesday are required streak days; Friday is optional. The optional finisher is excluded from the base duration estimate.

### Scoped workout starts

The Plan page can start:

- The complete plan.
- One section.
- One individual exercise, including all of its sets.

All scopes use the same player engine to avoid divergent timer, pause, audio, wake-lock, and session-saving behavior.

### Current interaction and architecture pass

- Countdown number animation was removed.
- Countdown audio continues to use a 50 ms synchronization check and shared audio context.
- All remaining animation and transition durations are capped at 2 ms.
- Plan sections are closed by default.
- Exercise metadata is always rendered below the exercise name.
- Numeric form fields can remain empty while being edited; empty strings are not coerced to zero.
- Validation errors reset when the user changes relevant input.
- Save and Save & Load are separate plan actions.
- Loading screens wrap persistence operations in preparation for asynchronous APIs.
- Plan management actions remain Edit/Delete on the left and Load on the right.
- Application pages and reusable UI elements were split into dedicated modules.
- ShadCN’s open-code composition approach was adopted for reusable UI primitives.
- TypeScript path aliases are defined once in the root and application configs; duplicate JSON configuration is treated as a build-blocking regression.
- The TypeScript 5.9 configuration uses the valid `ignoreDeprecations: "5.0"` threshold; version-specific compiler settings must match the installed compiler.

### Plan-management feature decomposition

Plan management was split from one combined editor/library component into a feature directory with:

- A dedicated `usePlanEditor` hook for draft state, immutable mutations, numeric editing buffers, validation, normalization, and submission.
- Separate Plan Editor and Plan Library pages.
- Focused components for plan basics, live metrics, sections, exercises, editor actions, library cards, management headers, and delete confirmation.
- Shared plan-management types and schedule formatting.
- A compatibility barrel at the former import path so application orchestration remains stable.

This boundary keeps stateful form logic independent from presentation and makes individual plan-management behaviors testable without loading the entire application shell.

## 5. Data Model

### Workout plan

```ts
type WorkoutPlan = {
  id: string;
  name: string;
  workoutDays: number[];
  optionalWorkoutDays?: number[];
  blocks: WorkoutBlock[];
  createdAt: string;
  updatedAt: string;
};
```

Required workout days participate in streak calculations. Optional workout days display the workout but do not break a streak when missed.

### Section

```ts
type WorkoutBlock = {
  id: string;
  name: string;
  shortName: string;
  optional?: boolean;
  exercises: Exercise[];
};
```

### Exercise

```ts
type Exercise = {
  id: string;
  name: string;
  type: "timed" | "reps";
  sets: number;
  durationSeconds?: number;
  reps?: string;
  restSeconds: number;
  note?: string;
};
```

`durationSeconds` drives timed exercises and estimates rep-based work duration. `reps` is a display target and intentionally supports ranges and descriptive values.

### Session

Sessions are `completed`, `partial`, or `skipped` and are linked to a plan ID. Legacy sessions without a plan ID are associated with the built-in plan.

## 6. Player and Timer Technique

`buildSteps` converts plan sections into a linear player sequence. This pure transformation is also used for section-only and exercise-only sessions.

Timed intervals store an absolute deadline:

```text
remaining = ceil((deadline - current timestamp) / 1000)
```

The UI refresh interval is not treated as elapsed time. This avoids drift when the browser throttles timers or the tab is backgrounded.

The 3–2–1 cue check runs every 50 ms. A shared `AudioContext` avoids repeatedly paying audio initialization latency. A per-second guard prevents duplicate ticks, and an advancing guard prevents duplicate transitions at zero.

The countdown number itself does not animate.

## 7. Duration and Streak Rules

Plan metrics are derived from exercise data:

```text
work = estimated work seconds × sets
rest = rest seconds × max(sets - 1, 0)
```

Optional sections are excluded from the base duration estimate. Sets and section totals include the complete plan.

Streaks inspect only the active plan’s required workout days. Optional workout days and rest days are skipped during the streak walkback.

## 8. Forms and Validation

Plan-editor state is updated immutably with array `map`, `filter`, and object spread operations.

Numeric inputs maintain a separate string editing buffer. This permits a user to clear `60`, see an empty field, and type a replacement without React immediately forcing `0`. Saving is blocked while a numeric field remains empty.

Validation errors are cleared on relevant input changes so stale messages do not remain after correction.

## 9. UI and Accessibility Principles

- Large touch targets and one-handed mobile layout.
- Text labels accompany icons where meaning is not otherwise obvious.
- Audio never carries unique information.
- Buttons have accessible names for section and exercise starts.
- Loading feedback uses `role="status"` and `aria-live="polite"`.
- Exercise name and metadata are separate vertical text rows.
- Singular and plural labels are generated from counts.
- The Plan page defaults to collapsed sections to reduce visual noise.

## 10. Animation Policy

Motion remains installed for component lifecycle hooks and future tuning, but current product policy caps every animation and CSS transition at 2 ms. The countdown value has no animation. Repeating loading rotation was removed.

Any future animation change must preserve the user-requested maximum unless this requirement is explicitly revised.

## 11. Loading and Backend Migration

Plan save, load, and delete actions pass through a loading-screen boundary. They currently use local persistence and a short operation wrapper. When Firestore is introduced, replace the local operation with awaited API work while retaining the same UI boundary and error recovery path.

## 12. Persistence

Current storage keys are centralized in `lib/storage.ts`. Loaders catch malformed JSON and fall back safely. Plan objects are stored as a complete collection; the active plan has a separate key.

Do not scatter new storage keys through page components.

## 13. PWA Strategy

Vite PWA uses `generateSW`, automatic update registration, and precaches the built application shell. Workout execution is client-side so a loaded workout is not dependent on a live network request.

`dist/` is generated output, ignored by Git, and may be safely removed after verification. The requested workflow is to clear it after testing to conserve disk space.

## 14. Verification Checklist

For behavior changes:

1. Run TypeScript and the production build with `npm run build`.
2. Test the primary mobile viewport.
3. Verify full-plan, section, and exercise starts when player code changes.
4. Verify create, edit, save, save-and-load, load, and delete when plan state changes.
5. Confirm active-plan streak filtering and history ownership.
6. Run `npm audit --omit=dev --audit-level=high` after dependency changes.
7. Inspect the exact generated `dist` path and remove it after tests when requested.
